# Compatibility architecture audit

Audit of checkout a3d964973230964640e6bc7abff5e91ab0324e6b. This is an inventory, not an implementation of the proposed compatibility layer.

* Terminal links use `ShareUtils.openUrl`, which dispatches an `ACTION_VIEW` intent. Other UI paths also launch intents directly.
* `TermuxOpenReceiver` is private. It dispatches non-file URIs from a broadcast with `NEW_TASK`; file paths are separately converted to provider content URIs with read grants. Changes to browser launching must preserve the latter path and its existing access checks.
* Shell environment construction begins in `AndroidShellEnvironment`, `TermuxShellEnvironment` and `TermuxAppShellEnvironment`. Interactive profile scripts can subsequently change it. Managed jobs have a separate execution path; see `docs/next-generation/managed-jobs-appshell-audit.md`.
* `ShellCompatibility.ensure()` writes an app-owned profile script, prepends a checked glibc exec shim to an existing preload, and may restart an interactive login bash once. `glibc-exec.c` switches loader and preload environment across runtime boundaries. Existing documentation says managed jobs do not receive automatic glibc compatibility.
  The shim inspects only the first 4096 bytes of an ELF file and passes files outside that bound through unchanged. ELF64 offsets and sizes with nonzero upper bits are rejected rather than truncated; this bounded detection does not establish that a loader, shared libraries, or kernel features will work on a device.
* `termux-open` and `termux-open-url` belong to the installed termux-tools package, not this source tree. Their installed versions and command behavior need device verification before changing integration.
* ControlCore and JSON-RPC v1 are existing interfaces. No compatibility RPC is implemented by this audit.

The manifest requests internet and network-state permissions, declares the open receiver non-exported, and exposes a file provider with its existing access policy. The project builds with min SDK 21, target SDK 28 and compile SDK 36. Package visibility and activity launch behavior require tests at the relevant target/API combinations; a successful `startActivity` cannot establish visibility.

The opt-in network test uses the process default Android resolver and route for DNS and HTTPS; it does not change resolver settings, trust settings, network binding, or CLI environment. The app reports its own Android trust result only. A response from the fixed endpoint does not establish the health of another host, and IPv4/IPv6 DNS records do not establish family-specific reachability. Network metadata is a snapshot and can change during the test.

Upstream `termux-tools` scripts inspected on 2026-11-03: [`termux-open`](https://github.com/termux/termux-tools/blob/master/scripts/termux-open.in) sends a broadcast to the private receiver; [`termux-open-url`](https://github.com/termux/termux-tools/blob/master/scripts/termux-open-url.in) calls `am start` directly and supports an optional package/component. Both use `TERMUX__USER_ID` when valid and otherwise fall back to user 0. These are upstream source observations, not evidence of the version installed on any device. The new receiver path therefore cannot fix direct `termux-open-url` launches or the upstream fallback for secondary users. A safe, package-manager-aware integration that preserves the optional component argument remains to be designed and tested.

The optional localhost check binds temporary sockets to `127.0.0.1` and `::1`, uses bounded connect and accept timeouts, verifies the accepted connection is its own, and closes the sockets. It is a loopback primitive test, not an OAuth implementation or external-browser callback test. It cannot diagnose an individual CLI's port, redirect URI, state, PKCE, token exchange or authorization timeout.

The user-initiated browser callback probe is a distinct ephemeral listener, bound only to IPv4 loopback. Its random path is not an OAuth redirect URI, and it never handles a real CLI's authorization codes or tokens. It accepts only the exact test request, discards other request data without recording it, and closes after a result, a bounded number of connections or a deadline. The listener does not persist across process death.

The bundled ARM64 bootstrap archive examined locally contains `termux-tools` version `1.46.0+really1.45.0-1`; its two URL scripts match the broadcast/direct-launch split above. This does not establish the package version on an upgraded installation. Shell setup now supplies `TERMUX__USER_ID` from the process UID when no inherited value exists. It uses the [AOSP UID composition](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/core/java/android/os/UserHandle.java) (`uid / 100000`), not the separately exposed user serial. Existing explicit environment and managed-job overlays retain precedence. This mapping and the CLI commands have not been verified on secondary-user or work-profile hardware.

The optional app-owned v1 wrapper resides under `$TERMUX_APP__FILES_DIR/compat-v1/termux-open-url`; it is installed without replacing existing entries and never modifies a package-managed executable. One-argument HTTP(S) URLs are handed to the existing `termux-open` receiver. Other schemes and calls with an explicit package/component delegate to the installed `termux-open-url`. The wrapper does not change `PATH` or `BROWSER` itself. Because it is opt-in, unmodified calls to the package's direct command still bypass the receiver.

`termux-compat` runs on demand in the caller's shell environment. DNS and HTTPS observations are separate: a missing `getent` is reported unavailable, and a curl HTTP response remains a response even for 401/403. It uses the bundled `timeout` and curl's own deadlines, refuses to run the network probes without the timeout executable, suppresses tool output and credentials, ignores curl configuration files, leaves TLS verification on, and unsets TLS key logging only inside the curl subprocess. It does not diagnose all resolvers, CA stores, architectures, proxies or network failure causes, and never changes device networking.

A passive compatibility profile is shown in the app and, when available, as an optional `compatibility` field on the existing same-UID ControlCore `system.describe` response. The snapshot is bounded and contains Android/target SDK, ABI, user-ID and device/kernel metadata. It does not run network, browser or executable tests. Its broad dynamic states remain `UNKNOWN`, so a network change cannot leave a global success claim; the background receiver entry describes the app's deferred-user-action policy rather than asserting that a browser will launch. No method, permission, listener or protocol version was added.

After an explicit Android network test, discovery may expose a separate in-memory observation scoped to that one example.com probe. It keeps only status, HTTP code, age, network identity and configuration hashes. Default-network and link/capability callbacks invalidate it; a state recheck and a 60-second lifetime provide additional bounds. Registration is attempted only on API 24+, and failure leaves the observation unavailable. Network changes can race with callback delivery and response serialization, so clients must treat the value as historical and the broad capability as unknown. No network check is triggered by `system.describe`, and Android state is read on the connection worker, not the service thread.

Optional IPv4 and IPv6 TCP samples use the process default route and at most one resolved address each. They are skipped if an Android VPN or proxy, JVM proxy, explicit process binding, or uncertain proxy policy is detected. They do not change process or socket network binding, bypass a detected VPN/proxy, or establish TLS success. A policy change can race with a connection; before/after checks mark detected changes as inconclusive. The separate ControlCore network observation does not expose these family samples.

TLS failures are classified from exception types and, on API 24+, structured [certificate-path reason codes](https://developer.android.com/reference/java/security/cert/CertPathValidatorException.BasicReason). Android documents that [certificate-path errors can arise from an unknown CA or incomplete chain](https://developer.android.com/privacy-and-security/security-ssl); the classifier does not infer which from exception messages. Exception messages, certificate contents, response bodies and credentials are not retained. Certificate expiry and not-yet-valid statuses indicate a disagreement with the device's clock, not which side is wrong. Bundle diagnostics only test fixed paths for file readability; they do not add certificates, alter CA variables or compare Android and CLI trust stores.
