# Implementation status against the unified SDK, jobs, files and workspaces spec

This file records what the repository implements, what was verified and where, and what remains. It is not a release claim. Every PR below is device-verified on one arm64 phone; PR 6 (signed release, other ABIs and API levels, profiling) is still open.

Host verification: Linux x86_64, JDK 21, the cached Gradle wrapper offline, NDK 29. Devices: Xiaomi 22021211RG (Android 14, kernel 4.19) and Poco X3 Pro M2102J20SG (Android 16, kernel 4.14, ROM that refuses `run-as`), both arm64-v8a with debug builds installed over ADB. On the Poco the device checks run inside Termux with `device_jobs_e2e.py --local`; all 34 pass.

## Running-job control

Kernel 4.19 lacks `clone3`, pidfd signalling and `close_range`, so managed jobs use the owned child launcher described in `managed-jobs-appshell-audit.md`. The app forks the child itself, waits without reaping (`WNOWAIT`), and signals only before marking the child exited, so a signal can never reach a recycled PID. `system.describe` reports `limits.jobStopAvailable`. If the native library cannot load, it is `false`, and timeouts and running-job cancel return `UNSUPPORTED` as before.

## Next steps, in order

1. Release-signed build with an upgrade and rollback check.
2. Another ABI (armeabi-v7a or x86_64) and an older Android version on hardware.
3. Richer UI. The long-press menu now has Managed jobs (list, newest 16 KiB of each stream, cancel), Files (read-only browsing of `home` and `prefix` through the race-safe access, links listed and never opened, UTF-8 previews of the first 16 KiB) and Workspaces (list, presets, and "Open terminal here", which starts a new session in the workspace directory and leaves existing sessions unchanged). All three are dialogs that load off the main thread; the session menu, consent dialog and key editor were checked by screenshot on the Poco. Not built: file editing, multi-select, SAF picker, image preview, a process tree with job actions, and running presets from the UI.
4. Optional: a durable job journal. Spec §4.3.6 allows documenting service-lifetime history instead, which is the current behavior: job records and output live in memory, a service restart forgets them, and no job is ever reported as surviving a restart.
