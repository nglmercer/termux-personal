# Managed jobs: AppShell integration audit

This is an implementation audit, not a claim that managed jobs are available. The existing `RUN_COMMAND` path and session API remain unchanged.

* `TermuxService.createTermuxTask(ExecutionCommand)` calls `AppShell.execute` while holding the service monitor. `Runtime.exec` runs before that method returns, so managed job startup must happen on a bounded worker and must not hold the service thread across process creation.
* `AppShell.executeInner` starts separate stdout and stderr `StreamGobbler` threads, then waits for the child and joins both readers. `StreamGobbler` uses `BufferedReader.readLine()` and appends to `ResultData` string builders. A long line or unbounded output can consume unbounded memory, byte fidelity is not preserved, and verbose logging may contain output. This capture path is unsuitable for managed jobs.
* Legacy nonempty stdin gets a newline appended and is closed afterward. Empty stdin is not closed until after `waitFor`, which may leave a child waiting for EOF. Managed jobs need a distinct bounded exact-byte stdin policy and must close their pipe independently without altering plugin semantics.
* `AppShell` starts its worker before `createTermuxTask` registers the returned object in the task list. A managed job must reserve and publish its own record before launch and reconcile an immediate exit or startup failure exactly once.
* `kill()` looks up a numeric PID and sends `SIGKILL` through `Os.kill` (the comment mentions SIGILL, but the code uses SIGKILL). This is not a safe cancellation primitive for a separately managed job because the PID can be reused. New cancellation must operate on the owned process handle, with bounded grace and explicit descendant limitations.
* `onAppShellExited` posts a short removal/notification callback to the service handler. It is not a durable job journal; process death, force-stop, and reboot do not guarantee retained history or continuing work.

`JobOutputStore` is a bounded, service-lifetime foundation that reuses the existing byte replay buffer. `JobStreamPump` drains one byte stream into the store and keeps draining if retention is unavailable. `AppShellJobCapture` connects both pumps and an exact bounded stdin writer to the worker-only `AppShell.executeManaged` hook. `JobIoPool` reserves three worker slots per admitted capture, at most four captures, with bounded worker and queue counts. Reservations are retained until the actual worker tasks exit, even if their futures were cancelled. Host tests cover EOF, simultaneous large output, drain timeout and an uninterruptible worker. These components are not yet wired into `TermuxService` or IPC. Interrupting a blocked reader is not guaranteed to close a pipe held by descendants; the reservation then remains occupied and the coordinator must report resource pressure rather than overcommit. Before enabling jobs, implement the coordinator, consent scopes, idempotency, owned-handle cancellation and lifecycle cleanup, then run on-device tests.

`JobRegistry` now reserves output and pipe capacity before publishing records and retains request fingerprints for its service lifetime. Identical requests in the same authorization epoch replay the record; conflicting requests or reuse in a different epoch fail without exposing the previous record. Its current conservative retention policy refuses admission after the record limit instead of evicting idempotency keys. This is an internal foundation, not a job API: authorization and executable/cwd policy are still required before admission. The future coordinator must stop owned live processes before closing the registry; closing it alone does not terminate children.

`AppShellJobAdapter` connects an admitted record to the worker-only managed capture path, returns the actual `Process` handle, and handles callbacks that arrive before launch returns. It requires the caller to authorize and resolve the executable and working directory. For managed execution it retains the Termux environment but bypasses Termux's interpreter argument rewrite so that the process receives the requested argv; legacy shell execution is unchanged. The adapter alone does not implement cancellation, timeouts, service ownership, or an IPC feature, and its Android backend still requires device verification.

The internal `JobCoordinator` combines admission with bounded launch workers, checks its injected path policy at admission and again before launch, and can cancel queued jobs without launching them. `JobAuthority` supplies opaque, server-issued leases with separate read, output, execute and cancel permissions. Replacing or revoking consent invalidates older leases; a final short check marks launch in flight, so revocation after that check does not guarantee the child never starts. It refuses requested wall timeouts while running-child termination is unavailable. Shutdown stops new admission and queued jobs; it will not close the registry while a launched child remains unresolved. The coordinator and authority are not connected to `TermuxService`, local consent or RPC. Safe live-child shutdown, real consent integration and device tests remain release blockers.

`JobPathPolicy` provides worker-only checks against server-configured executable and working-directory roots and a fixed mapping for bare executable names. It rechecks root resolution, file type and execute permission before launch and currently rejects workspace IDs. Canonicalization detects ordinary symlink escapes but is not an atomic containment boundary: a same-UID process can swap a path after the check and before execution. The policy must not be represented as protecting a filesystem boundary or used to enable the API until the launch/authorization threat model and race-safe handling are resolved. `JOBS_EXECUTE` itself authorizes commands with the app UID and can modify app-owned files regardless of file-write scope.

Coordinator metadata listing and bounded output reads are independently authorized. A newly granted read or output scope can inspect retained records from an earlier consent epoch; cancellation remains restricted to the epoch that created the job. Output reads return a consistent finished flag and end offset, so a reader does not mistake an append racing with completion for end of stream. These are in-process interfaces only and do not advertise new RPC methods.

`OwnedProcessControl` handles the stop-before-handle race and one bounded grace timer, but Android signalling is deliberately unavailable. Android implementations of `Process.destroy()` vary: [an older implementation](https://android.googlesource.com/platform/libcore/+/5d930ca/luni/src/main/java/java/lang/ProcessManager.java) used SIGKILL, while [another implementation](https://android.googlesource.com/platform/libcore/+/master/ojluni/src/main/java/java/lang/UNIXProcess.java) documents a PID-reuse race. The Android SDK exposes `destroyForcibly()` only from API 26, and its existence alone does not prove an identity-safe graceful-then-force sequence. A signalling handle must be acquired atomically with child creation, or another identity-safe mechanism demonstrated, before enabling cancellation. Opening a pidfd from a PID obtained after Java process creation can itself race with process exit and reuse. Managed AppShell no longer calls `Process.destroy()` as cleanup; it waits for child exit even when capture or worker startup fails. Capture retains its reservation until that exit. A child that never exits can therefore retain a worker and quota indefinitely; safe live-child cleanup and service shutdown still need implementation before managed jobs are enabled. Cancellation requests currently return unsupported without changing job state; an exit after a requested stop is recorded as an observed exit, not presumed to have been caused by the request.

`managed-fork.c` is an unconnected native primitive that uses `clone3(CLONE_PIDFD)` to acquire a pidfd atomically with child creation. It has no numeric-PID signalling fallback. A child created from a multithreaded Android process must execute only async-signal-safe native code before `exec` or `_exit`; it must never return to Java. The host test (`bash scripts/test-managed-fork-host.sh`) checks close-on-exec, signalling, immediate exits, stale handle rejection and an exact-argv native exec; it passed on Linux x86_64 in this workspace. `scripts/test-managed-fork-abi.sh` cross-compiled the primitive for all four supported Android ABIs with NDK 27/API 21. This is not a packaged or integrated process launcher, and compilation does not prove that `clone3` or pidfd signalling is allowed by any Android kernel or seccomp policy. JNI, pipe and exec-error handling, descriptor-relative paths, lifecycle cleanup and real-device tests are still required; unavailable syscalls must produce an unsupported capability.

`managed-path.c` adds an unconnected root-descriptor-relative, no-symlink traversal primitive. It pins directory and regular-file descriptors with close-on-exec; `O_PATH` avoids opening special files before checking their type. `bash scripts/test-managed-path-host.sh` checks traversal, symlink escapes, special files, and replacement of a name after opening. The ABI compilation script also compiles this code. This does not establish safe root acquisition or execution, and it does not by itself prevent concurrent directory renames, hard links, mount changes, or changes to a file's contents. Integration and device tests remain necessary before treating it as a security boundary.

The host pidfd test also exercises `execveat(AT_EMPTY_PATH)` on a close-on-exec `O_PATH` descriptor for an ELF executable after replacing its pathname with a symlink to a different executable. This is a host-only probe, not proof of Android support or script compatibility; interpreter scripts can have different descriptor and close-on-exec requirements. The production launcher and fallback behavior remain unimplemented.

The native prototype now has a child-only `fchdir`/`execveat` helper that reports pre-exec errors over a close-on-exec pipe and exits without returning to Java. Its host test covers successful execution and a working-directory failure; all four ABI compilers accept it. Parent-side launch, pipe ownership, integration and Android validation are still absent.

A parent-side status reader bounds the wait and rejects partial error messages. EOF with no error is deliberately reported only as pipe closure: a child can die before reporting an error, so EOF alone does not prove execution. Callers must retain ownership of the child and reconcile its actual outcome. The helper requires a single reader and correct closure of other pipe writers.
