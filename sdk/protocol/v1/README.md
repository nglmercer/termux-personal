# Termux control protocol v1 contract

`methods.json` lists implemented methods and their required scopes. Multiple scopes are required together; `outputService` methods also require the output service to be available. `binaryDirection` describes the additional frame after request metadata or response metadata. The Java registry is checked against this file by `ControlMethodRegistryTest`.

After `system.hello` negotiates version 1, `system.describe` returns the authorized and available methods with their scope requirements, mutation and binary metadata, and transport limits. `system.capabilities` remains available to older clients. A client talking to an older server must treat `-32601` from `system.describe` as an optional-feature absence and use `system.capabilities`. The hello response and frame format remain unchanged.

This contract describes the session methods and the managed job (`job.*`), process (`process.list`), file (`file.roots`, `file.list`, `file.stat`, `file.read`) and workspace (`workspace.*`) methods. Each domain is advertised only when the server wires its service and the user granted its separate, unchecked-by-default consent in the app; otherwise its methods are absent from `system.describe` and return `-32601`. File methods are wired only with descriptor-relative, no-follow traversal, so a concurrent directory or link swap cannot redirect them.

Workspace Git notes: `workspace.git` runs only the fixed inspection argv (`status`, `branch`, `diff`, `log`) and needs `WORKSPACES_READ` and `JOBS_EXECUTE`. `workspace.git.change` needs `WORKSPACES_WRITE` and `JOBS_EXECUTE` and runs `fetch --prune`, `pull --ff-only --no-rebase`, `switch BRANCH`, `add -- PATHS` or `commit -m MESSAGE`. A branch must pass a conservative ref-name check and cannot start with `-`. Paths are workspace-relative and follow `--`. A message is only ever the value of `-m`. Both methods return a managed job whose exit code and output report Git's result. `push` is not offered. Hooks, filters and configuration in the repository can run code, which is why every Git method needs job execution consent.

File write notes: `file.mkdir`, `file.rename`, `file.delete` and `file.transfer.*` need `FILES_WRITE` and a root that `file.roots` reports as `writable` (only `home`). `file.rename` never overwrites. `file.delete` removes a regular file or an empty directory; `recursive: true` returns `UNSUPPORTED`. A transfer writes to an owner-only `.termux-upload-*` file beside the destination, strictly in order: `file.transfer.write` accepts only the next offset, or an exact repeat of bytes already written. Commit requires the declared length and the `sha256` given at begin, syncs, and then renames. Without `overwrite` it never replaces an existing entry; with `overwrite` the destination must still have the `ifRevision` given at begin, or the commit fails with `STALE_REVISION`. A failed commit discards the transfer. Revisions combine mtime and size, so a same-second, same-size change is not detected. At most 4 transfers are open at once, up to 2 GiB each; an idle transfer expires after 15 minutes and its temporary file is removed. A rejected chunk closes the v1 connection, as for any rejected binary request, so clients cannot abort on that connection and the transfer expires instead. Local control remains opt-in, and scopes are chosen by the server, not by client request fields.

Job method notes: `job.start` requires `executable` and an exact `args` array; `cwd` must be an absolute normalized path (workspace-relative paths are not implemented), and `presentation` defaults to `background`. Results never include executable, arguments, environment or stdin. Running jobs can be stopped only when `system.describe` reports `limits.jobStopAvailable: true`: the server then owns each child's identity (it alone reaps it, so a signal never reaches a recycled PID), accepts nonzero `timeoutMs`, and `job.cancel` sends TERM to the job's process group and KILL after a 10-second grace. Descendants that left the group may survive. When it is false, a nonzero `timeoutMs` and cancelling a launched job return `UNSUPPORTED`; queued jobs can always be cancelled. A stopped job ends as `cancelled` or `timed_out` with a null `exitCode`; a job stopped because the service is shutting down ends as `exited` with `128 + signal`. `job.cancel` returns `{accepted:true}` without a state field. `job.output.read` adds `finished` and `complete` to the session-style offset metadata. Job methods run on the connection worker rather than the service thread, because the coordinator resolves paths. Domain failures use the reserved names in `errors.json` inside the `-32001` family.

`schemas/request.json` and `schemas/response.json` describe the JSON-RPC envelope; they do not replace the server's bounded parser or method-specific validation. `errors.json` records legacy error families and reserves names for future domain errors. A request with a binary payload is one JSON metadata frame followed by one binary frame; response metadata is followed by a binary frame only when the declared length is nonzero. The connection remains serialized and does not support batches or unsolicited messages.

`schemas/method-params.json` and `schemas/method-results.json` provide definitions keyed by method name. `fixtures/methods.json` contains a structural example for each registry entry, including binary-frame bytes where applicable. The TypeScript contract test checks fixture coverage, schema validity, and selected invalid cases. These schemas do not encode authorization, service state, output offsets, parser depth or all UTF-16 length constraints; the server remains authoritative.
